## 1. 배경

선생님 수업 화면을 설계하던 중 **수업 일정·배정 시스템이 존재하지 않는다**는 사실이 확인되었다. 수업 화면은 그 시스템의 7개 엔드포인트 뒤에 스텁을 두고 먼저 만들기로 했고, 이 문서가 그 스텁을 대체할 진짜 시스템을 정의한다.

### 1.1 주 사용자는 선생님이다

범위를 나눌 때 이 시스템의 주 사용자를 운영자로 적었으나, 인터뷰 결과 **보강 예약을 선생님이 직접** 하기로 확정되면서 바뀌었다. 선생님이 자기 일정과 보강을 스스로 관리하고, 운영자는 등록·배정·감독을 맡는다.

선생님 수업 화면에서 세운 원칙 — **시스템이 밀지 않고 선생님이 당긴다** — 이 여기서도 그대로 적용된다.

### 1.2 확정된 전제

| 항목 | 값 |
|---|---|
| 학생-선생님 관계 | **고정 담임.** 같은 선생님과 계속한다 |
| 일정 생성 | **반복 시간표 + 추가 예약** |
| 결석·취소 시 | **보강으로 살린다.** 잔여 횟수 관리 |
| 보강 예약 주체 | **선생님이 직접** |
| 담임 부재 시 | **휴강 후 보강.** 대체 선생님 없음 |
| 수업 시간대 | **15:00 ~ 20:00**, 10분 단위 슬롯 |
| 크레딧 유효기간 | **멤버십 유지 기간 내내** |
| 휴강 신청 마감 | **하루 전** |
| 노쇼 판정 | **시작 후 10분** |
| 공휴일 | **수업 없음** |

## 2. 이 설계에서 사라진 것 — 담임 부재의 처리

고정 담임의 가장 큰 약점은 담임이 못 나올 때다. 흔한 해법은 대체 선생님 배정이고, 그러면 가능 선생님 풀, 매칭 규칙, 이력 인계, "처음 보는 선생님" 문제가 줄줄이 따라온다.

**담임 부재를 휴강 + 보강으로 처리하기로 하면서 그 전부가 사라졌다.** 학생 결석과 완전히 같은 경로를 탄다. 대체 선생님 시스템을 만들지 않는다.

이것이 이 설계에서 가장 큰 단순화이며, 고정 담임의 장점(관계·맥락 유지)도 함께 지킨다.

## 3. 데이터 모델

```
Student ──┐
          ├── Enrollment ── 담임 관계 + 잔여 보강 크레딧
Teacher ──┘        │
                   ├── RecurrenceRule    예: 매주 화·목 19:00
                   │         │ 4주치 롤링 생성
                   │         ▼
                   └────── Session ────── 상태 · 메모 · 누적끊김 · 준비상태
                              ▲
                   MakeupCredit ── 발생(휴강·결석·노쇼) → 소비(보강 예약)
```

### 3.1 Session을 미리 만들어 둔다

반복 규칙에서 즉석 계산하지 않고 **4주치를 실제 행으로 생성**한다. 수업 하나가 자기 상태를 가져야 하기 때문이다 — 선생님 메모, 누적 끊김 시간, 학생 준비상태, 재입장 가능 여부.

**규모**: 선생님 3,000명 × 하루 최대 30슬롯 = 이론상 하루 90,000건. 실제 가동률을 절반으로 잡아도 4주치 100만 건 미만이며, 일반적인 관계형 DB로 충분하다.

### 3.2 크레딧은 Enrollment 단위

크레딧은 학생 개인이 아니라 **담임 관계에 붙는다.** 담임이 바뀌면(운영자 재배정) 크레딧을 어떻게 이관할지 정해야 한다(§8 오픈이슈).

## 4. 수업 상태

```
SCHEDULED ──5분 전──▶ LOBBY_OPEN ──선생님 시작──▶ IN_PROGRESS ──종료──▶ ENDED
    │                      │                            │                │
    ├─ 휴강(하루 전까지) ───┴──────────▶ CANCELLED       │                │
    │                                        │           │                │
    └─ 시작 후 10분 경과, 또는 ──────────▶ NO_SHOW ◀─────┘                │
       선생님이 [노쇼 처리]                   │                            │
                                              ▼                            │
                                    보강 크레딧 +1                          │
                                                                           ▼
                                                          ENDED +30분까지 재입장 가능
```

`ENDED` 이후 30분 재입장은 수업 화면 설계 §4.3에서 이미 요건이 되었다. 종료 확인 다이얼로그를 없앤 대가로 되돌릴 길을 연 것이다.

### 4.1 노쇼 판정 — 자동 10분 + 선생님 재량

**수업 길이가 10분인데 노쇼 판정도 10분이면, 판정되는 순간 수업은 이미 끝나 있다.** 자동 판정만 두면 선생님은 어떤 경우에도 슬롯 하나를 통째로 기다려야 한다.

슬롯이 10분 그리드로 붙어 있어 다음 수업이 곧바로 오므로 실질 손해는 그 슬롯 하나에 그친다. 따라서 자동 기준으로는 10분이 타당하다. 그러나 아이가 3분 만에 안 올 것이 분명한 날도 있고, 9분에 오는 날도 있다.

**선생님이 언제든 [노쇼 처리]를 눌러 조기 종료할 수 있게 한다.** 기다릴지 접을지는 선생님이 판단한다. §1.1의 원칙 그대로다.

자동 판정은 선생님이 아무 조치도 하지 않은 경우의 안전망으로만 동작한다.

### 4.2 휴강

- **하루 전까지** 신청할 수 있다. 기준 시각의 정확한 정의는 §8 오픈이슈.
- 신청 주체는 선생님(자기 사정)과 운영자(공휴일 등 일괄)다.
- 마감을 넘긴 뒤의 취소는 휴강이 아니라 **노쇼로 처리**된다. 크레딧은 동일하게 발생하므로 학생이 손해 보지는 않으며, 차이는 기록상의 구분과 통계뿐이다.

### 4.3 공휴일

공휴일에는 수업이 없다. 반복 규칙에서 Session을 생성할 때 **애초에 만들지 않는다.**

따라서 **공휴일은 크레딧을 발생시키지 않는다.** 없어진 수업이 아니라 처음부터 없던 수업이기 때문이다. 매주 2회인 학생은 그 주에 1회만 하게 된다. 이 해석이 운영 의도와 다르면 §8 오픈이슈로 조정한다.

한국 공휴일 달력이 필요하며 **대체공휴일을 포함**해야 한다. 매년 갱신되므로 운영자가 수정할 수 있어야 한다.

## 5. 보강 크레딧

### 5.1 발생과 소비

| 발생 사유 | 크레딧 |
|---|---|
| 학생 결석 (사전 통보) | +1 |
| 학생 노쇼 | +1 |
| 담임 부재로 휴강 | +1 |
| 운영 휴강 | +1 |
| **공휴일** | **없음** (§4.3) |

소비는 하나뿐이다 — **선생님이 자기 빈 슬롯에 보강 수업을 만들 때.**

### 5.2 유효기간은 멤버십 기간

크레딧은 **멤버십이 유지되는 동안 소멸하지 않는다.** 고객 입장에서 옳은 정책이다.

⚠️ **다만 운영 리스크가 있다.** 담임의 빈 슬롯은 하루 최대 30개로 유한하다. 결석이 반복되는 학생은 크레딧이 쌓이는데 그것을 소진할 자리가 없어질 수 있다. 크레딧이 무한히 쌓이면 서비스가 갚을 수 없는 부채가 된다.

**대응**: 소멸시키는 대신 **누적 크레딧이 임계치를 넘으면 선생님과 운영에 경고**를 띄운다. 방치되지 않게 하는 것이 목적이며, 임계치는 §8 오픈이슈다.

멤버십이 해지되면 잔여 크레딧은 소멸한다.

## 6. 화면

### 6.1 선생님용 (주 사용자)

| 화면 | 내용 |
|---|---|
| 내 일정 | 오늘/이번 주. 수업 화면의 목록과 같은 데이터를 쓴다 |
| **휴강 신청** | 자기 수업을 못 하게 됐을 때. 하루 전 마감 검증 |
| **보강 예약** | 담당 학생의 잔여 크레딧을 보고 자기 빈 슬롯에 배치 |
| 담당 학생 | 학생 목록 + 각자의 잔여 크레딧 + 누적 경고 |

보강 예약 화면은 **자기 빈 슬롯을 그리드로 보여주고** 학생을 끌어다 놓는 형태가 자연스럽다. 15:00~20:00 × 10분이면 하루 30칸이라 한 주가 한 화면에 들어온다.

### 6.2 운영자용

학생·선생님 등록 · **담임 배정** · 반복 시간표 설정 · 전체 일정 조회 · **공휴일 관리** · 크레딧 수동 조정(예외 상황) · 누적 크레딧 경고 목록

### 6.3 보호자용 — 이번 범위에서 제외

조회조차 만들지 않는다. 결석 통보는 현행 경로(선생님·운영 연락)를 쓴다. 필요해지면 별도 스펙으로 다룬다.

## 7. 수업 화면과의 접점

선생님 수업 화면이 스텁으로 쓰고 있는 **7개 엔드포인트가 그대로 진짜 구현이 된다.** 인터페이스는 바뀌지 않는다 — 그러려고 그렇게 정의했다.

추가로 필요한 것은 셋뿐이다:

| 엔드포인트 | 용도 |
|---|---|
| `POST /sessions/{id}/cancel` | 휴강 신청. 하루 전 마감을 검증하고 크레딧을 발생시킨다 |
| `GET /teacher/{id}/makeup-slots` | 내 빈 시간 + 담당 학생별 잔여 크레딧 |
| `POST /makeups` | 보강 수업 생성. 크레딧을 소비한다 |

노쇼 조기 처리는 기존 `POST /sessions/{id}/end` 에 사유를 실어 재사용한다.

## 8. 이 설계가 하지 않는 것

정산·급여 · 결제 · 보호자 앱/화면 · **대체 선생님** (§2) · 학생-선생님 매칭 알고리즘(고정 담임이라 불필요) · 학습 리포트

## 9. 오픈 이슈

| # | 항목 | 비고 |
|---|---|---|
| 1 | **선생님 한 명당 담당 학생 수** | 미정. 세션 생성량과 보강 예약 화면 밀도에 영향 |
| 2 | **"하루 전"의 정확한 정의** | 24시간 전인가, 전날 자정까지인가 |
| 3 | **누적 크레딧 경고 임계치** | §5.2. 몇 개부터 경고할지 |
